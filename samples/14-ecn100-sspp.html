1.0  Introduction

1.1  Purpose

This System Security and Privacy Plan (SSPP) documents the security and privacy controls implemented for the Expeditionary Command Node (ECN-100), in support of an Assessment and Authorization (A&A) decision under the DoD Risk Management Framework (RMF), per DoDI 8510.01. Controls are drawn from NIST SP 800-53, with impact levels assigned per CNSSI No. 1253.

In plain terms: this document tells the Authorizing Official (AO) what the system is, what risks it carries, and what has been done to manage those risks, so the AO can decide whether to grant it permission to operate.

1.2  Scope and Applicability

This SSPP applies to all hardware, software, and firmware physically installed within the ECN-100 shelter/trailer and its organic radio and satellite communications (SATCOM) equipment. It does not cover the networks the ECN-100 connects to once established in theater; those are addressed under Section 4.0, Interconnections, and governed individually by Interconnection Security Agreements (ISAs).

2.0  System Identification

2.1  System Name, Mission, and Ownership

The Expeditionary Command Node (ECN-100) is a trailer- and shelter-mounted mobile command and control (C2) platform. It houses a self-contained tactical local area network, SATCOM terminal, and line-of-sight (LOS) radio relay equipment, and operates on generator power, vehicle power, or shore power depending on the deployment scenario.

Unlike a fixed facility, the ECN-100's authorization boundary moves with the platform. It is designed to stand up, operate, and displace within a single operational period, which drives several of the control decisions in Section 5.0 — particularly physical security during transit and continuity of operations when connectivity is lost.

The ECN-100 carries two connected enclaves: SIPRNET (classified, Secret) and NIPRNET (unclassified but sensitive). Both enclaves route over the same physical SATCOM uplink but remain logically and cryptographically separated end to end. A separate, physically isolated NIPRNET segment is also present for local administrative use; because it is air-gapped, it has no external connectivity and is not part of either enclave's interconnection path.

Primary connectivity for both connected enclaves is via the FTX-2400 FTSAT. Should the FTSAT be unavailable — due to obstruction, maintenance, or displacement to a new location — the ECN-100 falls back to alternate connectivity over high-speed civilian infrastructure (commercial broadband or cellular data service where available), used strictly as an unencrypted bearer for traffic that is already encrypted before it reaches that bearer.

Navy message traffic (fleet broadcast) is received independently of the FTSAT data path, primarily via UHF SATCOM with HF as the alternate receive path.

Workstations. The permanent workstation baseline consists entirely of laptops: four GCCS-M workstations on SIPRNET processing OTH-T Gold Red/White/Blue track data for contact reporting, one SIPRNET administration workstation, and one dedicated NIPRNET workstation. Additional workstations can be added to either enclave as mission requirements warrant.

The ECN-100's SATCOM suite consists of two terminals. An INMARSAT B terminal provides a lower-data-rate commercial backup path. An FTX-2400 Flyaway Tri-Band SATCOM Terminal (FTSAT) — a Commercial-Off-The-Shelf (COTS), 2.4-meter transportable terminal operating across C-, X-, and Ku-band — serves as the primary high-data-rate uplink, compatible with DSCS, NATO, INTELSAT, EUTELSAT, PANAMSAT, and DOMSAT satellite systems, and capable of hub-independent set-up, acquisition, and operation without depending on a specific ground station configuration.

The ECN-100 provides a deployable C2 capability for a supported unit operating away from garrison infrastructure: voice and data connectivity back to higher headquarters, local situational awareness display, and short-term data storage for mission-essential functions.

4.0  Interconnections

The ECN-100 maintains two external network enclaves, each governed by its own Interconnection Security Agreement (ISA), executed prior to connection and reviewed at each reauthorization cycle. Both enclaves share the same physical uplink hardware but never share a cryptographic boundary — SIPRNET traffic is protected by Type 1 encryption regardless of which physical bearer carries it, which is what makes the civilian-infrastructure fallback acceptable as an alternate path rather than a separate risk decision.

Appendix C — Control Implementation Procedures

C.1  Implementing Access Control for the ECN-100 Network

Performed during pre-deployment configuration, before the ECN-100 leaves garrison.

  1. Provision PKI/CAC-based authentication against a local, on-platform identity store, replicated from garrison before departure so the ECN-100 does not depend on a live connection back to a garrison domain controller.
  2. Configure role-based access control (RBAC) groups for each crew position (watch officer, communications operator, system administrator).
  3. Configure an offline/local authentication fallback for use during disconnected, intermittent, or limited-bandwidth (DDIL) operations. Fallback credentials are single-use and time-limited, and every use is logged for review at the next reconnection.
  4. Disable or remove any default or vendor accounts on installed equipment.
  5. Document any control not fully implementable in the mobile environment, and the compensating measure in place, in the POA&M (Section 7.0).

C.2  Executing Incident Response in a DDIL Environment

DDIL — disconnected, intermittent, or limited-bandwidth — is the operating condition the ECN-100 is built around. This procedure assumes the platform cannot call back to a garrison Security Operations Center (SOC) at the moment an incident is detected.

  1. Detect and isolate the affected system or segment from the rest of the ECN-100 LAN.
  2. Contain locally using on-platform tools; do not wait for reachback connectivity.
  3. Log all actions taken, with timestamps, to the local audit store. Local logging is mandatory because the audit trail may be the only record available until a garrison SOC begins its own review.
  4. Continue mission-essential operations on unaffected systems where possible.
  5. Upon reconnection, report the incident and transmit local logs to the garrison SOC per the unit's incident reporting timeline.
  6. Participate in an after-action review and update local procedures or the POA&M as needed.
